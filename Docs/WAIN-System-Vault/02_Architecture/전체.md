# 1. 프로젝트 개요

## 1.1 프로젝트 명칭

**WAIN System — A World-Agent Interactive Narrative System for Visual Novels**

한국어 설명:

**비주얼 노벨을 위한 월드-에이전트 인터랙티브 서사 시스템**

WAIN은 플레이어의 자유형 자연어 입력을 처리하면서 캐릭터의 지속적인 경험, 게임 세계의 상태, 제작자가 의도한 서사 진행을 일관되게 관리하는 LLM 기반 시스템이다.

특정 게임 자체보다는 **다른 비주얼 노벨 프로젝트에도 적용할 수 있는 독립적인 Unreal Engine C++ Plugin**을 목표로 한다.

별도의 **Visual Novel Testbed**를 제작하여 Plugin의 기능을 통합 검증한다.

## 1.2 프로젝트의 문제의식

전통적인 Visual Novel은 제작자가 Dialogue, Choice, Branch를 사전에 정의한다.

이 방식은 정밀한 서사 통제가 가능하지만 플레이어의 의사 표현이 사전 정의된 선택지에 제한된다.

LLM을 활용하면 자유로운 자연어 상호작용이 가능하지만, LLM만으로 게임을 구성하면 다음 문제가 발생한다.

| 문제 | 설명 |
|---|---|
| Character Consistency | 성격, 가치관, 말투, 배경 설정의 일관성을 지속적으로 유지하기 어려움 |
| Long-term Character State | 과거 경험, 관계 변화, 감정적 맥락이 장기적으로 유지되지 않을 수 있음 |
| World State Consistency | 생성된 대사·행동이 실제 게임 세계와 모순될 수 있음 |
| Narrative Control | 자유형 대화가 제작자가 설계한 서사적 목표와 정보 공개 범위를 이탈할 수 있음 |

따라서 단순히 VN에 LLM 챗봇을 연결하는 것이 아니라, **LLM 외부에서 상태와 서사 진행을 명시적으로 관리하는 Agent Architecture**를 설계한다.

## 1.3 프로젝트의 3대 목표

**① Persistent Character Experience**

- Persona에 해당하는 성격·가치관·말투 등 비교적 고정적인 설정 유지
- 경험과 관계 변화의 지속적인 누적
- 장기 Memory를 통한 이전 경험의 후속 대화·행동 반영

**② World-Aware Interaction**

- 현재 World State를 고려한 캐릭터 응답 및 행동 생성
- 상호작용으로 확정된 세계 상태의 지속적 반영
- 게임 세계와 모순되는 행동 제어

**③ Coherent Narrative Progression**

- 제작자가 정의한 Narrative Goal 및 Constraint 관리
- 플레이어의 자유형 입력을 허용하면서 서사적 진행 유지
- Narrative Beat의 완료 및 조건부 전이 관리

이 세 목표는 각각 Character Agent, World State Manager, Narrative Manager에 대응한다.

## 2.2 현재 연구 범위

초기 프로토타입은 다음 조건으로 한정한다.

- Single-Agent Visual Novel
- Turn-Based Interaction
- 플레이어와 캐릭터 간 대화에 의해서만 State 갱신
- 한 번에 하나의 Interaction 처리
- LLM 응답 생성 중 추가 플레이어 입력 및 독립적인 세계 상태 변경 없음
- 게임 세계의 실시간 자율 변화 미지원
- Multi-Agent 동시 상호작용 미지원

이 제한은 최종 발표에서 **연구의 한계(Limitations)**로 명시하기로 했다.

다만 비동기 LLM 호출은 사용한다. Unreal Engine의 Game Thread를 차단하지 않기 위한 비동기 처리와, 게임 상태가 동시에 변경되는 동시성 문제는 서로 구분한다.

초기 버전에서는 State Revision 기반 Optimistic Concurrency Control을 구현하지 않는다.

# 3. WAIN 전체 아키텍처

## 3.1 핵심 구성 요소

**Interaction Orchestrator**

플레이어의 한 번의 상호작용을 시작부터 종료까지 조율한다.

**Character Agent**

캐릭터의 상태, 경험, 기억, 계획을 관리하고 LLM을 이용하여 캐릭터의 대사와 행동을 생성한다.

**World State Manager**

WAIN 내부 또는 외부 게임 시스템이 소유하는 World State에 대한 통합 조회·검증·변경 인터페이스를 제공한다.

**Narrative Manager**

Narrative Graph, Goal, Constraint, Narrative State를 관리하고 현재 서사의 진행과 전이를 제어한다.

**Response Validator**

LLM이 생성한 대사와 행동 제안이 데이터 형식, 게임 규칙, 서사 제약을 만족하는지 검증한다.

**Shared LLM Service**

각 모듈이 필요에 따라 사용하는 공통 LLM 호출 추상화 계층이다.

**Embedding Service**

Memory Retrieval에 필요한 Embedding 생성 및 의미 유사도 검색을 지원한다.

**VN Testbed**

플레이어 입력 UI, 캐릭터 일러스트, 표정, 배경, 대사 출력 등 게임 표현을 담당한다.

## 3.2 책임 분리 원칙

WAIN에서 각 State의 소유권을 명확히 구분한다.

| State | 소유 모듈 |
|---|---|
| Persona | Character Agent |
| Relationship State | Character Agent |
| Emotion State | Character Agent |
| Character Memory | Character Agent |
| World Facts | World State Manager 또는 연결된 외부 Game System |
| Narrative Progress | Narrative Manager |
| Active Beat / Completed Beats | Narrative Manager |

**Source of Truth 원칙:** 동일한 상태를 둘 이상의 시스템이 독립적으로 관리하지 않는다.

Interaction Orchestrator는 각 모듈의 실행을 조율하지만, 직접 캐릭터 행동을 결정하거나 세계 상태를 소유하지 않는다.

LLM 또한 World State나 Narrative State의 최종 소유자가 아니다.

# 4. Interaction Pipeline

## 4.1 확정된 기본 흐름

**Player Input → Context Preparation → Character Agent → Response Validation → Narrative Evaluation → State Commit → VN Response**

각 단계의 역할은 다음과 같다.

| 단계 | 작업 |
|---|---|
| 1. Player Input | 플레이어의 자유형 자연어 입력 |
| 2. Context Preparation | World Context 조회 및 Narrative Context 구성 |
| 3. Character Agent | Memory·State·Plan을 활용한 응답 및 변경 제안 생성 |
| 4. Response Validation | 출력 형식, 게임 규칙, Narrative Constraint 검증 |
| 5. Narrative Evaluation | 승인 예정 변경을 기준으로 Beat 완료·전이 조건 평가 |
| 6. State Commit | 검증된 Character·World·Narrative 변경 실제 적용 |
| 7. VN Response | 확정된 대사·표정·행동을 게임 화면에 출력 |

## 4.2 중요한 설계 결정

### State Commit은 VN Response보다 먼저 수행

초기 제안서에서는 응답 출력 이후 State Update처럼 표현한 부분이 있었다.

하지만 현재 설계는 **Validation → State Commit → VN Response** 순서다.

State Commit은 단순히 변경 예약을 의미하지 않는다. 해당 변경을 실제 State에 적용한다.

VN은 성공적으로 확정된 결과를 시각적으로 표현한다.

### LLM 결과는 State가 아닌 Proposal

Character Agent가 대사를 생성하고 아이템 전달을 제안하더라도, 실제로 아이템을 전달한 것은 아니다.

구조적으로는 다음을 구분한다.

- Dialogue: 생성된 자연어 대사
- Expression: 표정 등 표현 데이터
- Narrative Action: 연출용 서술
- Executable Action: 실제 게임 상태 변경을 요구하는 행동
- State Change Proposal: 관계, 감정 등 변경 제안

실행 가능한 Action은 Validation과 Commit을 거쳐야 실제 결과가 된다.

### Narrative Evaluation은 승인 예정 변경을 기준으로 수행

현재 Beat의 완료 조건을 평가할 때 실제 Commit 전이므로, 검증된 변경이 적용된다고 가정한 상태에서 평가한다.

그 결과를 State Commit 단계에서 확정한다.

### Commit 실패 시

관련 상태 변경이 실패했는데 Narrative Beat만 진행되거나, 성공하지 않은 행동을 대사로 출력해서는 안 된다.

초기 프로토타입에서는 다음 정책을 우선한다.

- 변경 전 유효성 검사
- Game Thread에서 순차적 Commit
- 초기 구현에서 실패 가능성이 높은 외부 작업 제한
- 실패 시 해당 상호작용의 확정 응답 중단 또는 Fallback
- 복잡한 다중 소유 시스템 트랜잭션과 롤백은 초기 범위에서 제외

완전한 All-or-Nothing 트랜잭션이 이미 보장되는 것은 아니다.

# 5. Character Agent 상세 설계

## 5.1 Character Agent의 책임

Character Agent는 자신에게 전달된 Player Input, World Context, Narrative Context를 기반으로 다음을 수행한다.

1. Character State 참조
2. Memory Retrieval
3. 필요 시 Reflection 수행
4. 필요 시 Planning 수행
5. LLM 기반 Response Generation
6. Dialogue, Action, State Change Proposal 반환

Character Agent 내부에 LLM을 한 번만 호출하는 구조가 아니다.

Reflection, Planning, Response Generation 등의 기능이 필요할 때 공통 LLM Service를 각각 호출한다.

## 5.2 Character State

### Persona

캐릭터의 비교적 고정적인 정체성이다.

포함 가능한 항목:

- 성격
- 가치관
- 말투
- 배경 설정
- 개인적 선호와 성향

일반적인 대화에서 수시로 변경하는 값이 아니다.

다만 제작자가 의도한 캐릭터 성장이나 중요한 서사 이벤트가 발생하면 명시적인 정책으로 변화할 수 있다.

### Relationship State

장기적인 관계 상태를 표현한다.

초기 항목:

- Affinity
- Trust

대화를 통해 점진적으로 변화하며, 다음 대화의 Character Response에 영향을 준다.

### Emotion State

비교적 단기적인 감정 상태를 표현한다.

초기 항목:

- Emotion Type
- Emotion Intensity

Relationship보다 빠르게 변화하거나 감쇠할 수 있다.

## 5.3 Character State Update

LLM이 Relationship 수치를 직접 임의의 숫자로 출력하는 방식보다는, 다음과 같은 **의미적 변화 제안**을 반환하는 방식을 추천했다.

예시:

- Relationship Direction: Increase / Decrease / Neutral
- Relationship Intensity: Small / Medium / Large
- Emotion Type: Nervous
- Emotion Intensity: Medium

이후 C++의 State Update Policy가 이를 실제 수치와 상태로 변환한다.

예를 들어 Trust의 IncreaseSmall을 제한된 수치 증가로 변환할 수 있다.

장점:

- LLM 출력의 불규칙성 축소
- 관계 변화량 통제
- 명시적 게임 이벤트에 의한 변화와 중복 적용 방지
- 평가 및 디버깅에 유리

실제 수치 범위와 증가·감소량은 아직 최종 확정되지 않았다.

# 6. Memory System

## 6.1 기본 설계

Generative Agents(Park et al., 2023)의 Memory–Reflection–Planning 구조를 주요 근거로 활용한다.

초기 WAIN에는 하나의 **Memory Stream**을 두고 다음 세 종류의 Memory를 저장한다.

- Observation
- Reflection
- Plan

별도의 복잡한 Memory Consolidation이나 Forgetting 기능은 현재 구현하지 않기로 했다.

이 두 기능을 임의로 다시 추가하지 말 것.

## 6.2 Memory 데이터 구조

개념적인 구조:

| 필드 | 의미 |
|---|---|
| MemoryId | 기억의 고유 ID |
| Type | Observation / Reflection / Plan |
| Content | 기억의 실제 자연어 내용 |
| CreatedAt | 생성 시점 |
| LastAccessedAt | 마지막 참조 시점 |
| Importance | 중요도 점수 |
| Embedding | 의미 검색을 위한 벡터 |
| SourceMemoryIds | 해당 기억을 생성하는 데 참조한 기존 Memory ID |
| Metadata | 추가 정보 |

`SourceMemoryIds`는 실제 Memory 간 출처 관계를 표현한다.

예를 들어 Reflection은 자신이 근거로 삼은 Observation들의 ID를 저장한다.

Content와 SourceMemoryIds는 역할이 다르다.

- Content: 무엇을 기억하는가?
- SourceMemoryIds: 그 기억은 어떤 경험에 근거하는가?

## 6.3 Memory Retrieval

기본 검색 기준:

**Relevance + Recency + Importance**

- Relevance: Embedding 기반 의미 유사도
- Recency: 최근성
- Importance: 경험의 중요도

관련 Memory를 Top-K로 검색해 LLM Context에 전달한다.

현재로서는 BM25나 Hybrid Search를 초기 구현에 추가할 필요가 없다는 방향으로 논의했다.

Embedding 의미 검색과 필요시 ID·Metadata 기반의 정확한 필터링을 우선 사용한다.

가중치, 정규화 방식, Top-K 등은 아직 최종 수치가 확정되지 않았다.

Embedding 서비스는 `IEmbeddingService` 등으로 추상화한다.

## 6.4 Reflection

단순한 Observation 저장을 넘어, 축적된 경험으로부터 상위 수준의 해석을 생성한다.

예시:

Observation:

"플레이어가 반복적으로 딸기우유를 선택했다."

Reflection:

"플레이어는 딸기우유를 좋아하는 것 같다."

Reflection은 Memory Stream에 다시 저장하여 이후 Retrieval에 사용한다.

### Reflection Trigger

매 턴 무조건 Reflection을 실행하지 않는다.

Generative Agents에서 사용한 것처럼 경험의 누적 중요도에 따라 Reflection을 실행하는 방식을 기본으로 한다.

논의했던 원 논문 기반 절차:

1. 최근 경험의 중요도 누적
2. 임계값 도달 시 Reflection 실행
3. 최근 Memory를 바탕으로 중요한 질문 생성
4. 각 질문에 대해 관련 Memory 재검색
5. 관련 기억에서 통찰 생성
6. 결과를 Reflection Memory로 저장

원 논문을 참고한 예시 파라미터는 중요도 임계값 약 150, 최근 Memory 100개, 질문 3개, 질문별 최대 5개의 Insight 등이었으나, 이는 **WAIN의 확정 상수가 아니라 원 연구를 참고한 초기 설계 후보**다.

서로 관련 없는 최신 경험을 모두 섞는 것이 아니라, 질문별 관련 기억을 다시 검색해 주제적 일관성을 확보한다.

## 6.5 Planning

Generative Agents의 Planning을 참고하지만, VN 환경에 맞게 변형한다.

원 연구의 일일 일정 기반 Planning을 그대로 재현하기보다는, WAIN에서는 **Goal-Based Planning**을 사용한다.

Plan 요소:

- Goal
- Steps
- Conditions
- Current Step
- Status
- Active Plan ID

예시:

Goal: 플레이어에게 딸기우유 선물하기

Steps:

1. 플레이어의 선호 기억 검색
2. 선물 가능 여부 판단
3. 딸기우유 준비
4. 적절한 만남에서 선물 제안

Plan은 여러 턴에 걸쳐 유지될 수 있다.

Plan의 자연어 내용은 Memory Stream에 저장하되, 현재 어느 단계까지 수행했는지 등 실행 상태는 별도로 유지할 수 있다.

캐릭터의 Plan은 Narrative Manager가 설정한 전체 서사 Goal 및 Constraint 내에서만 수행한다.

실제 아이템 소유와 전달 가능 여부는 World State에 근거하여 검증한다.

# 7. Character Agent의 외부 인터페이스

개념적으로 다음 형태를 논의했다.

**ICharacterAgent::ProcessAsync(Request, OnComplete)**

Request:

- InteractionId
- CharacterId
- PlayerInput
- WorldContext
- NarrativeContext

Result:

- Response
- StateChanges
- MemoryOperations
- Status

Agent 내부의 Character State와 Memory는 해당 Agent의 관리 영역에서 조회한다.

Orchestrator가 Reflection 및 Planning 내부 단계까지 모두 직접 관리하지 않는다.

단, Interaction이 여러 번 동시에 실행되어 상태 충돌이 발생하는 문제를 줄이기 위해 초기에는 한 캐릭터당 한 번에 하나의 Interaction만 처리한다.

Reflection과 Planning에서 생성된 Memory를 어느 Commit 경계에서 저장할지에 대한 세부 정책은 추가 구체화가 필요하다.

# 8. World State Manager 상세 설계

## 8.1 역할

World State Manager는 게임 세계에 대한 **통합 State Query 및 State Commit 인터페이스**다.

주요 책임:

- WAIN 소유 State 저장·조회
- 외부 Game State 접근
- State Schema 검사
- 변경 요청의 소유 시스템 분배
- 승인된 상태 변경의 실제 적용
- 다른 모듈에 World Context 제공

## 8.2 Internal State + External Adapter

**Internal State Store**

WAIN이 직접 소유하는 상태를 저장한다.

예시:

- 게임 자체에 별도의 날씨 시스템이 없는 경우 Weather
- WAIN에서 직접 관리하기로 정한 World Flags

**External State Adapter**

외부 Unreal Engine 게임 시스템이 소유하는 상태에 대한 조회·변경 인터페이스다.

예시:

- Inventory System
- Actor / Object State
- 기존 게임의 Location 또는 Weather System

이미 게임의 Inventory System이 열쇠 소유권을 관리한다면 WAIN이 중복된 인벤토리를 생성하지 않는다.

해당 상태는 Adapter를 통해 조회하고, 변경도 실제 Inventory System에 요청한다.

초기 프로토타입에서는 Internal State 구현을 중심으로 하고, External Adapter는 **인터페이스 정의까지만** 진행한다.

## 8.3 Hybrid State Model

두 방식의 장점을 결합한다.

**Core World State**

여러 게임에 공통으로 필요한 최소한의 정보를 명시적인 구조로 표현한다.

후보:

- CurrentLocation
- WorldTime

단, Core에 포함될 정확한 필드는 아직 확정되지 않았다.

**Custom World Facts**

게임별로 필요한 다양한 상태는 Typed Key–Value 형태로 저장한다.

예시:

| Key | Type | Value |
|---|---|---|
| Door.IsOpen | bool | false |
| Door.IsLocked | bool | true |
| Player.Health | int32 | 100 |
| Weather | FName | Rain |

이 방식은 새로운 게임 상태를 추가할 때 WAIN 핵심 구조를 매번 수정하지 않도록 한다.

## 8.4 Typed Variant와 State Schema

Typed Variant는 값의 실제 자료형을 보존하는 범용 Value 표현이다.

다만 Variant만으로 특정 Key의 허용 Type까지 보장할 수는 없으므로 State Schema를 함께 사용한다.

Schema 항목:

- Key
- Value Type
- Default Value
- Constraints
- Mutability
- Owner

예를 들어 `Door.IsOpen = 100`은 Schema에 따라 거부한다.

하지만 문을 열 수 있는 실제 조건까지 단순 Type Check로 검증하는 것은 아니다.

State Schema Validation과 게임 규칙 Validation은 구분한다.

Unreal Engine에서 `TVariant`, `USTRUCT`, `UPROPERTY`, Reflection, Save/Load를 어떻게 결합할지는 구현 단계에서 결정할 사항이다.

## 8.5 World Context

Character Agent에게 전체 World State를 무조건 전달하지 않는다.

현재 상호작용에 필요한 World Context만 제공하도록 설계한다.

여기에는 Narrative Manager의 정보 공개 정책이 적용되어야 한다.

World Context의 정확한 선택 기준과 API 형식은 아직 미확정이다.

## 8.6 World State에서 제외할 정보

다음 데이터를 단순히 다른 시스템이 참조한다는 이유만으로 World State에 중복 저장하지 않는다.

- Character Relationship
- Character Emotion
- Character Memory
- Active Narrative Beat
- Narrative Progress 전용 Flags

Narrative Progress는 Narrative Manager가 소유하며, 필요하면 World State와 별도로 통합 Context를 구성한다.

# 9. Narrative Manager 상세 설계

## 9.1 목표

Character Agent가 개별 캐릭터의 행동과 대사를 결정한다면, Narrative Manager는 이야기 전체의 진행 방향과 허용 범위를 관리한다.

핵심 책임:

- Narrative Definition 관리
- Narrative Graph 관리
- Narrative State 관리
- Narrative Goal 및 Constraint 제공
- 정보 공개 범위 사전 필터링
- Beat Completion / Transition 평가

## 9.2 Narrative Graph와 State Machine

Narrative Graph는 사건·서사 요소 및 그 관계를 표현하는 그래프다.

State Machine은 현재 상태 및 조건부 전이 규칙을 관리하는 실행 모델이다.

둘은 상호 배타적이지 않다.

WAIN에서는 **Narrative Graph로 서사 구조를 정의하고, 이를 State Machine 방식으로 실행**한다.

## 9.3 확정된 서사 계층

**Chapter → Sequence → Beat**

| 단위 | 역할 |
|---|---|
| Chapter | 큰 서사 구간, 장기 Goal·Constraint |
| Sequence | 중간 서사 목표를 중심으로 Beat를 묶는 단위 |
| Beat | 구체적 사건·정보 공개·서사적 변화를 표현하는 기본 실행 노드 |

Narrative Graph의 실제 노드는 **Beat**다.

Chapter와 Sequence를 별도의 그래프 노드로 표현하지는 않는다.

중요한 구분:

**Chapter와 Sequence는 단순 문자열 메타데이터가 아니라, 자신만의 Goal과 Constraint를 보유하는 독립적인 Definition 객체다.**

Beat에는 상위 Sequence의 ID가 있고, Sequence에는 상위 Chapter의 ID가 있다.

따라서:

Beat → Sequence Definition → Chapter Definition

순서로 상위 정보를 참조한다.

## 9.4 Scene과 Story Arc

Scene은 Narrative Beat와 다른 개념이다.

- Scene: 시간·장소·등장인물 중심의 장면
- Beat: 이야기에서 발생하는 의미 있는 서사적 변화

하나의 Scene에서 여러 Beat가 실행될 수 있다.

반대로 하나의 Beat가 여러 장소에서 달성될 수도 있다.

장소와 장면의 실제 상태는 World State 및 VN Testbed와 연계한다.

Story Arc는 여러 Chapter를 관통하는 장기적 갈등·변화 흐름으로 이해하지만, 초기 구현에서 별도 완전한 Story Arc 관리 시스템을 만들기로 확정하지는 않았다.

## 9.5 Narrative Definition

초기 개념 모델:

**Chapter Definition**

- ChapterId
- Goal
- Constraints

**Sequence Definition**

- SequenceId
- ChapterId
- Goal
- Constraints

**Beat Definition**

- BeatId
- SequenceId
- Goal
- Constraints
- Completion Condition
- Transitions

이들 Definition은 제작자가 작성하는 정적 서사 데이터다.

## 9.6 Goal 표현

Goal은 주로 **자연어 설명**으로 저장한다.

예시:

"유나가 플레이어에게 오래된 사진에 대한 첫 단서를 자연스럽게 공개한다."

단, **Goal 자체와 Goal의 완료 판정은 별개**다.

Completion Condition은 구조화된 조건으로 표현한다.

예시:

- Fact: `Story.FirstClueRevealed`
- Operator: Equals
- Value: true

이 예시의 Fact는 Narrative State 소유 데이터로 둘 수 있다.

LLM이 "첫 단서를 공개했다"고 임의로 주장하는 것만으로 Beat가 완료되는 것은 아니다.

검증된 공개 행동이 Commit되어야 한다.

## 9.7 Constraint 표현

**Soft Constraint**

자연어 중심의 표현 제약이다.

예시:

"유나는 과거를 이야기할 때 조심스럽고 망설이는 태도를 유지한다."

**Hard Constraint**

구조화된 규칙 중심의 상태·행동·정보 접근 제약이다.

예시:

- Type: InformationAccess
- Target: Secret.YunaIdentity
- Access: Denied
- ReleaseCondition: IdentityRevealUnlocked

다만 자유형 자연어 속 암시나 우회적 정보 공개는 구조화된 규칙만으로 모두 검증할 수 없다.

따라서 Narrative Manager의 정보 사전 필터링과 Response Validator의 선택적 의미 검증을 결합한다.

## 9.8 계층적 Goal 및 Constraint 처리

현재 Beat를 기준으로 Chapter와 Sequence의 Goal·Constraint를 참조하여 **Effective Narrative Context**를 구성한다.

Goal은 서로 다른 수준의 목표다.

- Chapter Goal: 장기 방향
- Sequence Goal: 중간 방향
- Beat Goal: 현재 직접 달성할 목표

Constraint는 기본적으로 상위에서 하위로 누적 적용한다.

하위 Beat가 상위 Constraint를 임의로 해제해서는 안 된다.

정보 공개가 허용되는 시점에는 명시적인 Release Condition 또는 유효 범위 정의가 필요하다.

## 9.9 정보 사전 필터링

**중요한 기존 설계 결정이다.**

Narrative Manager는 Character Agent의 LLM에 모든 비밀 정보를 전달하고 단순히 "말하지 마라"고 지시하는 방식만 사용하지 않는다.

현재 서사 단계에서 사용·공개할 수 있는 정보를 선별한 뒤 Character Agent에 Context로 제공한다.

그러나 정보 사전 필터링이 모든 환각 또는 추측성 비밀 공개를 방지하는 것은 아니므로, 필요에 따라 응답 검증을 실시한다.

## 9.10 Beat Transition

초기 버전은 **조건 기반 전이(Conditional Transition)**를 사용한다.

Beat마다 가능한 다음 Beat와 전이 조건을 정의한다.

예시:

현재 Beat: FIRST_CLUE

Completion: FIRST_CLUE_REVEALED = true

다음 후보:

- TRUST_YUNA
- DOUBT_YUNA

전이 정책:

- 현재 Beat가 완료되어야 전이 평가 가능
- 전이 조건을 충족하는 후보 중 선택
- 복수 조건 충족 시 Priority 사용
- 조건 충돌·정의 오류 시 임의 선택 금지
- 완료되었으나 다음 조건이 없으면 다음 Beat 활성화 보류 가능
- 초기에는 한 Interaction에서 최대 한 번의 Beat 전이를 권장

Façade처럼 후보 Beat를 점수화하여 동적으로 선택하는 알고리즘은 초기 범위에서 제외하고 후속 확장으로 남긴다.

## 9.11 Narrative State

초기 런타임 데이터:

- ActiveBeatId
- CompletedBeatIds
- BeatHistory

ActiveBeatId에서 상위 Chapter와 Sequence를 참조할 수 있으므로 해당 ID를 항상 중복 저장할 필요는 없다.

LLM 처리 중 세계 상태가 독립적으로 바뀌지 않는 초기 프로토타입에서는 Revision 기반 동시성 제어를 우선 구현하지 않는다.

# 10. Response Validation과 LLM Service

## 10.1 Response Validator의 검증 순서

**1차: Structured Output Validation**

- 출력 Schema 유효성
- 필수 필드 존재 여부
- Action Type 유효성
- 기본 자료형 검사

**2차: Deterministic Rule Validation**

- World State 및 소유권 확인
- Action 실행 가능 여부
- 허용 범위와 구조화된 Narrative Constraint 검사
- 현재 서사 상태에 적합한 행동인지 확인

**3차: 선택적 Semantic Validation**

다음처럼 자연어의 의미를 검토해야 하는 상황에 한해 추가 LLM 검증을 고려한다.

- 핵심 비밀의 우회적 공개
- 문맥상 서사 제약 위반
- 캐릭터 설정과의 의미적 모순

항상 두 번째 LLM을 호출하지는 않는다.

Latency와 API 비용을 줄이기 위해 위험도가 높은 응답에서만 수행하는 방식을 추천했다.

검증 실패 시 제한적인 재생성 또는 사전 정의된 Fallback Response를 사용한다.

Semantic Validation은 오류 가능성이 있는 보조 수단이며 절대적인 보증이 아니다.

## 10.2 Shared LLM Service

공통 추상화 계층 `ILLMService`를 두는 방향이다.

담당:

- 비동기 LLM 요청
- Provider 추상화
- 결과 반환
- 오류 처리
- Token Usage
- Latency
- Cost 기록

어떤 Prompt를 구성하고 결과를 해석할지는 해당 기능을 소유하는 모듈의 책임이다.

예를 들어 Character Agent의 Reflection Prompt는 Reflection 기능이 소유한다.

이와 별도로 `IEmbeddingService`를 두어 Memory Retrieval을 지원한다.

테스트에서는 Mock LLM으로 비동기 처리, Schema 및 상태 변경 흐름을 검증할 수 있게 설계한다.

# 11. 프로토타입 및 개발 계획

## 11.1 구현 방식

**WAIN Plugin**

- Unreal Engine C++

## 11.2 개발 단계

기존 제안서의 개발 계획:

| 시기 | 내용 |
|---|---|

| 10~11주차 | Character Agent, Memory, Reflection, Planning |
| 12~13주차 | World State Manager, Narrative Manager 및 Testbed 연동 |

현재는 아키텍처 기본 설계를 완료했으므로, 발표자료에서는 '설계 예정'으로 표시하지 않고 **기본 설계 완료 → 구현 → 통합 → 평가** 순서로 표시한다.

실제 일정은 구현 진행 상황에 따라 조정해야 한다.

# 12. 평가 및 검증 계획

## 12.1 단계별 시스템 비교

기존 제안서에서 다음 구성을 사용하기로 했다.

| 실험군 | 구성 |
|---|---|
| A | LLM Only |
| B | A + Character Agent |
| C | B + World State Manager |
| D | C + Narrative Manager |

동일한 테스트 시나리오와 가능한 동일한 입력 조건을 적용한다.

각 모듈을 단계적으로 추가하는 **누적 비교(Ablation 성격의 실험)**다.

단, 누적 비교만으로 모든 모듈의 독립적인 인과 효과를 완전히 분리할 수 있는 것은 아니므로, 각 단계별 검증 목표를 명확히 설계할 필요가 있다.

## 12.2 시스템 기능 평가

- 과거 경험의 정확한 기억 회수
- Relationship State 반영
- Persona 및 캐릭터 설정 유지
- World State에 적합한 응답
- Narrative Constraint 위반율
- Beat Completion 및 Transition의 정확성

## 12.3 응답 품질 평가

평가자 기반 5점 척도를 고려한다.

주요 항목:

- Character Consistency
- Contextual Appropriateness
- Naturalness

추가로 토큰 비용, 응답 지연시간 등의 시스템 효율성 지표를 수집할 수 있지만 필수 평가 항목으로 확정된 것은 아니다.

## 12.4 아직 필요한 평가 설계

- 테스트 시나리오 구체화
- 모듈별 비교에 적합한 입력 세트 작성
- 평가자 수 및 평가 절차
- LLM 모델·파라미터 통제
- 정답 기준과 자동 검증 규칙
- 반응 품질의 평가 기준표
- 여러 실행에서 발생하는 응답 편차 관리
- 핵심 제약 위반을 어떤 조건에서 판정할지 정의

# 13. 연구의 한계

사용자가 명시적으로 연구의 한계에 추가하라고 결정한 항목:

**대화 기반 상태 갱신만 지원한다는 점.**

발표용 설명:

본 연구는 턴 기반 비주얼 노벨 환경을 대상으로 하며, 게임 세계와 캐릭터의 상태 갱신은 플레이어와 캐릭터 간 대화 상호작용에 한정한다.

따라서 대화와 독립적으로 발생하는 시간 경과, 환경 변화, NPC의 자율 행동 등에 의한 실시간 State 갱신은 지원하지 않는다.

후속 확장 후보:

- 비동기 World Event
- NPC의 독립적인 자율 행동
- Multi-Agent Interaction
- State Revision 및 동시성 제어
- 외부 게임 시스템과의 완전한 Adapter 연동
- 동적 Beat Selection
- 복잡한 상태 변경 트랜잭션

**주의:** 이는 현재 연구가 실패하거나 부족하다는 뜻이 아니라, 프로젝트의 구현 및 검증 범위를 의도적으로 제한한 것이다.

# 14. 선행연구 및 발표용 참고문헌

## 14.1 Generative Agents (2023)

**Park et al. — Generative Agents: Interactive Simulacra of Human Behavior**

https://arxiv.org/abs/2304.03442

WAIN 참고 요소:

- Memory Stream
- Recency / Importance / Relevance Retrieval
- Reflection
- Planning
- 과거 경험을 행동에 반영하는 Agent 구조

WAIN의 Planning은 이 연구를 그대로 재현하지 않고 Goal-Based VN 환경에 맞게 변형한다.

## 14.2 Story Designer (2022)

**Story Designer: Towards a Mixed-Initiative Tool to Create Narrative Structures**

https://arxiv.org/abs/2210.09294

WAIN 발표자료에서 참고하기로 한 핵심 연구다.

주요 내용:

- Trope 중심 Narrative Graph
- 서사적 관습과 관계의 그래프 표현
- 제작자와 AI가 함께 서사 구조를 구성하는 접근

Trope는 반복적으로 사용되는 캐릭터 유형·서사 관습·플롯 장치 등을 의미한다.

이 논문의 Narrative Graph와 WAIN의 Beat 기반 런타임 실행 그래프는 정확히 같은 구조가 아니다.

## 14.3 GENEVA (2024)

**GENEVA: GENErating and Visualizing Branching Narratives Using LLMs**

Microsoft Research

https://www.microsoft.com/en-us/research/publication/geneva-generating-and-visualizing-branching-narratives-using-llms/

주요 참고 요소:

- Narrative Beat 기반 그래프
- Beat를 노드로 표현
- 사건 간 방향성 있는 연결
- 분기 및 합류가 가능한 서사 구조

WAIN의 Beat 기반 Narrative Graph에 직접적으로 참고하기 좋은 연구다.

다만 GENEVA는 분기 서사의 생성·시각화에 초점을 둔 연구이며, WAIN과 같은 런타임 Character State 관리 시스템을 구현했다는 뜻은 아니다.

## 14.4 Façade (2005)

**Mateas & Stern — Structuring Content in the Façade Interactive Drama Architecture**

https://doi.org/10.1609/aiide.v1i1.18722

주요 참고 요소:

- Drama Manager
- Beat Sequencer
- Preconditions
- Beat Priorities / Weights
- Story Tension
- Beat 내부 대화 행동 및 Mix-in
- 플레이어 상호작용에 따른 서사적 진행

Façade는 LLM을 이용해 새로운 대사를 자유롭게 생성하는 방식이 아니라, 제작자가 작성한 대사·행동을 동적으로 선택·조합하는 시스템이다.

Façade의 Beat는 일반적인 문학적 Beat보다 큰 실행 단위에 가까울 수 있다는 점도 논의했다.

WAIN 초기 버전에서는 Façade처럼 최적 Beat를 동적으로 탐색하지 않는다.

**조건 기반 Beat Transition을 먼저 구현하고, 동적 Beat Selection은 향후 확장으로 고려한다.**

## 14.5 추가적으로 언급한 연구 및 사례

- Interactive Narrative: A Novel Application of Artificial Intelligence for Computer Games — Riedl & Bulitko (2012)
- IBSEN — Director / Actor 역할 분리 연구
- Voyage — AI 생성과 세계 상태 관리의 분리 사례
- AI Dungeon — AI 기반 인터랙티브 스토리 사례
- Inworld AI — 게임용 AI Character Runtime 관련 사례
- Vaudeville
- Uncover the Smoking Gun

이들은 기존 제안서의 기술 동향·참고문헌 구성에서 활용했다.

**학술적으로 중요한 구분:** `Chapter → Sequence → Beat`의 WAIN 계층 구조는 앞선 논문 중 하나가 그대로 제안한 모델이 아니라, 일반적인 플롯 구성 단위를 WAIN의 요구사항에 맞춰 결합한 자체 설계안이다.

5. 같은 단계의 카드 크기와 여백이 일관적인지
6. 기존 제안서 디자인과 이질적이지 않은지
7. 한국어 줄바꿈이 부자연스럽지 않은지
8. 내용이 실제 최신 시스템 설계와 일치하는지
9. 부록에 이전 설계 표현이 남아 있지 않은지

사용자는 예전 발표자료처럼 단순한 도형과 텍스트를 이용해 직접 수정 가능한 슬라이드를 선호한다.

# 20. 설계에서 반복해서 강조한 핵심 원칙

**1. WAIN은 단순한 LLM Character Chatbot이 아니다.**

캐릭터 기억, 게임 세계 상태, 서사 진행을 독립적으로 관리하는 시스템이다.

**2. Character Agent / World State Manager / Narrative Manager는 동등하게 중요한 핵심 모듈이다.**

Character Agent 하나에 모든 기능을 몰아넣지 않는다.

**3. LLM은 공유 서비스이며 최종 State Owner가 아니다.**

**4. Character Memory와 World State는 다르다.**

예를 들어 문이 열려 있다는 사실은 World State이고, 캐릭터가 문이 열리는 것을 보았다는 경험은 Observation Memory다.

**5. Narrative Manager는 Character Agent가 사용할 정보를 사전에 선별한다.**

단순히 금지사항을 프롬프트에 적는 것만으로 끝내지 않는다.

**6. Goal 설명과 Goal 완료 판정을 구분한다.**

Goal은 자연어로 설명할 수 있지만 Completion과 Transition은 구조화된 조건으로 평가한다.

**7. Narrative Beat와 Scene을 혼동하지 않는다.**

Beat는 사건·변화이며, Scene은 장면이다.

**8. LLM 응답은 실제 게임 행동이 아니다.**

Validation 및 Commit을 거쳐야 게임 세계에 반영된다.

**9. Turn-Based 프로토타입에서는 불필요한 실시간 동시성 제어를 추가하지 않는다.**

**10. 논문의 기존 방법과 WAIN 고유의 설계 제안을 명확히 구별한다.**

# 21. 새 채팅의 작업 방식에 대한 요청

새 채팅에서도 다음 방식을 유지해 주길 바란다.

- 한국어로 설명하되 기술 용어는 영어를 병기
- 시스템 설계를 논의할 때 구체적인 사례와 데이터 구조를 사용
- 이미 확정한 사항을 불필요하게 다시 결정하지 말 것
- 논문이 실제로 제시한 내용과 WAIN의 자체 설계를 구분
- 새 아키텍처를 임의로 추가하지 말 것
- 구현 범위를 불필요하게 확장하지 말 것
- 복잡한 주제는 한 번에 모두 설명하지 않고 단계별로 진행
- 명확한 기술적 근거가 없는 주장은 검증
- 슬라이드는 기존 디자인을 우선하며 텍스트가 반드시 도형 안에 들어가야 함
- 기존 Google Slides는 편집 가능한 기본 도형·텍스트 위주로 유지
- 모든 슬라이드 서체는 **Noto Sans KR**
- 제목은 Bold, 설명은 Regular를 기본으로 하되 원본 서식도 고려
- 다양한 파스텔 색상과 Border를 사용
- 구현되지 않은 기능을 구현 완료로 표현하지 말 것
