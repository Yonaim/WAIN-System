# 커밋 메시지 작성 규칙

> **한 줄 요약:** 커밋 메시지는 변경 내용을 짧고 일관되게 찾을 수 있도록 아래 형식을 따른다.

## 형식

```text
<Type>(<Scope>): <한국어 설명>
```

- `Scope`는 변경 대상 모듈이나 하위 시스템을 표시하며 선택 사항이다. 범위가 넓거나 특정 모듈에 속하지 않으면 `<Type>: <한국어 설명>`을 쓴다.
- Scope는 저장소의 모듈명·컴포넌트명을 사용한다. 예: `WAINSystem`, `NarrativeManager`, `TestbedUI`.
- `Type`은 아래 표의 키워드만 사용한다.
- 키워드는 첫 글자만 대문자로 쓴다. 예: `Feat`, `Docs`, `Chore`.
- 콜론 뒤 설명은 한국어로 작성한다. 클래스명, 파일명, API처럼 번역하면 의미가 달라지는 기술 명칭은 원래 표기를 유지한다.
- 설명은 변경 사항을 구체적이고 간결하게 나타내며 끝에 마침표를 붙이지 않는다.
- 제목은 한 줄로 작성한다. 추가 맥락이 필요할 때만 빈 줄 뒤에 본문을 쓴다.
- 제목과 본문에서 병렬 항목을 나열할 때 가운데점 대신 쉼표를 사용한다.

## 허용 키워드

| 키워드 | 사용 목적 | 예시 |
|---|---|---|
| `Feat` | 사용자에게 보이는 기능 또는 시스템 기능 추가 | `Feat: 대화 응답 표시 기능 추가` |
| `Fix` | 잘못된 동작이나 결함 수정 | `Fix: 빈 상태 응답 처리` |
| `Docs` | 문서 추가·수정 | `Docs: 상태 모델 문서화` |
| `Style` | 동작 변경 없는 코드 형식·표기 정리 | `Style: 에이전트 모듈 형식 정리` |
| `Refactor` | 외부 동작을 바꾸지 않는 코드 구조 개선 | `Refactor: 컨텍스트 생성 로직 분리` |
| `Perf` | 측정 또는 명확한 근거가 있는 성능 개선 | `Perf: 상태 조회 경로 비용 감소` |
| `Test` | 테스트 또는 테스트 데이터 변경 | `Test: 응답 검증 사례 추가` |
| `Build` | 빌드 시스템·컴파일 설정 변경 | `Build: WAIN 플러그인 모듈 추가` |
| `CI` | 지속적 통합 및 자동화 파이프라인 변경 | `CI: Pull Request 빌드 검증 추가` |
| `Chore` | 기능·문서·테스트 변경에 속하지 않는 유지보수 | `Chore: 외부 의존성 갱신` |
| `Revert` | 이전 커밋 되돌리기 | `Revert: 대화창 애니메이션 변경 취소` |

한 커밋에 여러 종류의 변경이 섞이면 핵심 변경을 기준으로 키워드 하나를 고른다. 서로 독립적인 변경은 별도 커밋으로 나눈다.

## 예시

```text
Feat(NarrativeManager): 장기 상태 기반 응답 컨텍스트 생성
Feat: 단일 에이전트 테스트 시나리오 추가
Docs: 시스템 책임 경계 문서화
Refactor: 상태 검증 로직 분리
```
