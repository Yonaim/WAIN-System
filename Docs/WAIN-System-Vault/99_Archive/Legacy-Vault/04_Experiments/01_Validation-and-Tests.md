# 검증·테스트 계획

> 상태: 계획안. 여기에는 테스트 실행이나 결과를 기록하지 않았다.

## 검증 단계

### 계약·단위 검증

- 유효하거나 잘못된 구조화 모델 출력 파싱
- 알 수 없는 필드와 잘못된 타입 거부
- 소유권, 변경 권한, 범위, Hard Narrative Constraint 적용
- 설정된 위험 사례에서만 의미 검증을 호출하는지 확인
- 고정 Embedding과 결정론적 Fixture를 사용한 Memory 순위 확인
- Beat 완료, 전이 가능 여부, 우선순위, 전이 없음 동작 확인

### 파이프라인 통합 검증

- 유효한 응답은 비주얼 노벨에 성공 결과를 반환하기 전에 Commit한다.
- 잘못된 출력은 권위 있는 State를 변경하지 않는다.
- 필수 Commit 실패 시 Beat를 진행하거나 Commit 성공으로 보고하지 않는다.
- 중복·재시도 상호작용으로 State 변경을 조용히 중복 적용하지 않는다.
- 비공개 사실은 요청 구성 전에 Context에서 제외한다.
- 호스트 Adapter 실패와 정상적인 미등록·기본 World Fact를 구분한다.

### 시나리오 평가

고정된 캐릭터·월드·서사 초기 State를 가진 반복 가능한 시나리오를 만든다. 동일 입력을 A~D 단계에 적용하고 원시 출력을 보존한다. 품질 지표와 시스템 동작 지표는 평가 개요를 따른다.

## 사전에 정의할 통과 기준

구현 검증을 주장하기 전에 다음을 명시한다.

- 예상 응답 Schema와 허용 실패 경로
- 필수 일관성 규칙과 State 불변 조건
- 시나리오별 Narrative 전이 정답
- 1~5점 평가 기준
- 최소 표본 수와 확률적 실행 결과의 집계 방법
- 시간 초과, Provider 오류, 미완료 실행의 처리

## 결과 현황

설계 문서, 중간발표 자료, 발표 대본에는 실행 결과가 제공되지 않았다. 실제 실행 후 날짜가 있는 결과 기록을 추가하고 사용한 설정을 보존한다.
